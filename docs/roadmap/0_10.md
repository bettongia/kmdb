# v0.1.0

## Integration Guide

The specification's [System Overview](../spec/01_overview.md) provides a
high-level overview of the KMDB system for developers seeking to understand how
KMDB works, and the rest of the specification provides a deeper dive for those
interested in the inner workings of KMDB.

The "Integration Guide" will document how a developer can utilise KMDB in their
Dart or Flutter application. The document will describe how to create/open a
database; manage collections, documents and the vault; handle faults; etc. The
goal is to help developers to integrate KMDB into their application both quickly
and reliably.

As part of this guide, use a sample Flutter to-do application that demonstrates
the concepts described in the guide. The to-do application will have multiple
projects, each with their own list of tasks. Each task will have a title,
description, priority (high/medium/low), status (backlog/in-progress/done), file
attachments and comments (updates). This will provide a basis for demonstrating
database mechanics (open/close, update, create collection etc), schema,
indexing/search, vault, sync.

**Dependency:** this work moved out of `0_09.md` into its own roadmap because it
is a significant body of code and documentation in its own right — a new
`kmdb_example_todo` package plus the guide prose, not a docs-only change like
its former roadmap siblings. It depended on the
[Specification review and editing](completed/0_09.md) work item as a
prerequisite — the guide cites spec section numbers throughout, and that review
is what validates those sections are correct, complete, and current before the
guide builds on them. **That prerequisite is now satisfied**: `0_09` is
complete, so this plan can proceed.

> ### ✅ Former dependency (resolved 2026-08-10): the security model this guide documents has settled
>
> The
> [2026-07-18 release-readiness review](../reviews/release-readiness-review-2026-07-18.md)
> found that `docs/spec/31_encryption.md` documented a **passive-only** threat
> model and never claimed synced data was authentic (finding **E-1**). The
> decision taken in response was to **close that gap before `0.1.0`** on the
> [0.10.01 hardening track](0_10_01.md).
>
> This guide teaches developers how to set up sync and the vault, so it makes
> security claims — and those claims depended on that work landing first: sync
> artefacts become authenticated, sync gains a device-enrollment (`remote pair`)
> step, and §31's threat model was rewritten. Writing the guide any earlier
> would have documented a model that no longer held by the time `0.1.0` shipped.
>
> **That work has now landed** — sync authentication (WI-4) merged in
> [PR #74](https://github.com/bettongia/kmdb/pull/74) on 2026-08-10; see
> [plan_0_10_01_sync_authentication.md](../plans/completed/plan_0_10_01_sync_authentication.md)
> (split out of the original
> [sync trust boundary plan](../plans/completed/plan_0_10_01_sync_trust_boundary.md)).
> The blocker is cleared. This guide is the **closing readiness deliverable for
> `0.1.0`**: written last, against the frozen public API and the settled
> security model, so every claim it makes reflects the shipped code.
