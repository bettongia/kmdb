# v0.2.0

The first post-`0.1.0` release. This roadmap collects work that was
deliberately **deferred out of the `0.1.0` release gate** — items that are not
release-blocking for the first tag but are worth doing next — plus new work
that lands after `0.1.0` ships.

> This file is seeded from deferrals recorded during the
> [0.10.01 hardening track](0_10_01.md) and the
> [2026-07-18 release-readiness review](../reviews/release-readiness-review-2026-07-18.md).
> Items move here when the maintainer decides they are genuinely
> post-`0.1.0`, rather than being dropped or left implicit in the hardening
> roadmap.

## CLI session agent — unlock once, reuse across commands

`kmdb_cli` has **no DEK cache**, so every command that opens an encrypted
database runs full Argon2id (~200 ms). That is fine in the REPL and painful when
scripting a sequence of commands. The fix is an `ssh-agent` / `op signin`-shaped
session agent: the DEK lives in agent process memory (never on disk), bounded by
an idle timeout *and* an absolute cap, with `kmdb … lock` ending the session
immediately and the agent never outliving the login session.

This was split out of the 0.10.01 WI-5 unlock-policy plan
([PR #75](https://github.com/bettongia/kmdb/pull/75), which closed SC-1) on the
reviewer's recommendation and then **deferred out of the `0.1.0` release gate on
2026-08-26**. The reasoning: it is a CLI *ergonomics* improvement, not a
correctness item — it does not close SC-1, WI-5 already did — and it is the
single highest-risk new subsystem in that track, because it introduces a new
place a DEK lives. Shipping that under release time-pressure is the wrong trade;
`0.1.0` ships without a CLI DEK session cache.

The plan is still `Draft` with real open questions to close before it can reach
`Investigated`: the IPC transport (Unix domain socket on POSIX, but **Windows has
no Unix socket** and is a supported CLI/CI target — named pipe with an explicit
ACL?), socket/pipe location and discovery (`$XDG_RUNTIME_DIR` on Linux; macOS
and Windows have no direct equivalent), the wire protocol, per-OS enforcement of
"never outlives the login session", interaction with WI-5's
`KEKSource`/`ReauthPolicy` (the absolute cap must not exceed the re-auth
interval; `alwaysRequirePassphrase` should disable agent caching), and peer-
credential authorisation of a requesting process. In `0.2.0` it can go through
the full reviewer → implement → QA pipeline unhurried.

## Self-healing native-asset cache (dylib bundling flake)

`dart test`'s ONNX-runtime native-asset bundling step (copy →
`install_name_tool` → codesign of `libonnxruntime.*.dylib`) is intermittently
flaky in this environment — a truncated dylib after an interrupted build, or a
codesign race during bundling — and it surfaces through `make pre_commit`,
failing otherwise-clean (even doc-only) commits. The manual workaround is to
clear the native-asset cache and re-warm; this item automates that as a
`make heal_native_assets` target (and, if a bundled dylib can be rebuilt
offline, an optional retry-once-on-dylib-error guard around the commit hook's
test step). A dev-ergonomics improvement, not release-blocking; deferred so it
does not race the `0.1.0` integration-guide PR, which touches the same
Makefiles/CI.

- **Plan:**
  [plan_0_20_native_asset_heal.md](../plans/plan_0_20_native_asset_heal.md)
  (status: Draft — the make-or-break open question is whether clearing only the
  bundled dylib while keeping the downloaded artifact lets it rebuild offline)

## kmdb_icloud macOS native build verification in CI

The `kmdb_icloud` Swift plugin's native compilation is **not** build-verified in
CI. The 2026-07-18 release-readiness review (release-ninja finding **#3**) flagged
this blind spot: no CI lane ever compiles the plugin's Swift — `cicd_icloud` is
Dart-only, and `kmdb_flutter` has no macOS native code — so a native regression
would not be caught by the pipeline.

An attempt to close this in the 0.10.01 CI-hardening slice
([PR #87](https://github.com/bettongia/kmdb/pull/87)) added a
`flutter build macos --debug` step, which **failed on CI** and was reverted. A
local clean-checkout reproduction (2026-09-02) established the reasons and why
this is **not a `0.1.0` blocker**:

1. **The plugin itself compiles.** On a freshly-cleaned local tree the
   `FlutterFramework` SPM module resolved and the plugin's Swift compiled — there
   was no "unable to resolve module dependency: 'Flutter'" error. So this is
   **not** a consumer-facing SPM defect; `kmdb_icloud` builds for a consumer with
   their own signing set up. The CI "unable to resolve" error is most likely a
   cold-runner SPM-resolution ordering issue, not broken plumbing.
2. **The example cannot build unsigned on CI — a hard entitlements wall.** The
   iCloud example's `Runner` carries iCloud/CloudKit + push entitlements
   (`com.apple.developer.icloud-services: CloudKit`,
   `com.apple.developer.aps-environment`, an iCloud container id), which require
   a **real Apple Developer signing identity / provisioning profile**. An
   unprovisioned GitHub runner cannot satisfy them, and `--debug`'s ad-hoc
   signing is insufficient. This is inherent to it being an *iCloud* example.

**Why this is post-`0.1.0`, not a tag blocker.** The plugin compiles as shipped;
the only thing missing is CI *build-verification* of that native compile. KMDB
runs no mobile/iCloud device testing in CI at all — that would need access to
(simulated or real) Apple devices and an Apple Developer ID, neither of which the
pipeline has today. Adding macOS native build-verification for `kmdb_icloud` is
the same class of work as standing up that mobile/device CI capability, and is
better scoped as its own post-`0.1.0` effort than jammed into the release gate.

Candidate directions (to evaluate in the plan): build a CI-only variant of the
example with entitlements stripped so ad-hoc signing suffices; `xcodebuild` the
plugin scheme directly with `CODE_SIGNING_ALLOWED=NO` +
`-resolvePackageDependencies` (also addresses the cold-resolution ordering);
provision CI signing (heavy); or keep it as a documented manual
release-checklist build. iOS parity (a new `ios/` runner) is a further extension.
